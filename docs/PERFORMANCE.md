# 性能验证

此项目提供可复现的 HTTP 负载脚本，不附虚构性能结果。参考图片中的目标均未通过本仓库已有证据验证：

| 目标 | 所需验证 |
| --- | --- |
| 500+ 并发用户 | 同时在线长连接、连接成功率、资源占用、持续时间与消息速率 |
| 消息延迟 <100ms | 跨实例发送到接收的端到端 p50/p95/p99，明确网络和计时口径 |
| 50K+ 消息 | 真实规模数据下的写入、游标分页查询与索引执行计划 |
| 查询提速 60% | 相同硬件、数据、请求及缓存条件下与明确基线对照 |
| 99.7% 可用性 | 生产监控窗口、失败定义、故障演练及实际可用性记录 |

## HTTP 负载

安装 k6 后先启动应用，在自己有权测试的环境中执行：

```bash
k6 run scripts/load-http.js
BASE_URL=http://localhost:8080 VUS=50 DURATION=2m k6 run scripts/load-http.js
```

脚本为每个虚拟用户注册独立账号，从已有房间中选择一个，以约每用户每秒一次的节奏发送消息并读取最近 50 条历史。用户名和消息 UUID 每次运行重新生成，消息会保留在数据库中，运行前应使用可丢弃的测试数据库。默认 10 个虚拟用户、30 秒。

脚本阈值设为 HTTP 错误率 <1%、HTTP p95 <1000ms，属于本脚本的检查标准，**不代表截图中的 100ms WebSocket 目标**。注册或环境未就绪会令脚本失败。脚本只测试 HTTP 持久化与查询，不创建 WebSocket，不能据此宣称 500 个实时在线用户或跨实例广播延迟达标。

## WebSocket 与扩容验证

1. 部署至少两个应用实例，连接同一 PostgreSQL 和 Redis。
2. 两个浏览器使用独立账号连接同一房间，验证双向消息与断线历史补读。
3. 如需严格证明跨实例同步，在测试环境将两个客户端分别定向到不同实例，检查另一侧收到的消息 ID 与数据库记录一致。
4. 编写真实连接压测时，先使用 JWT 调用 `/api/auth/ws-ticket`，再以返回的单次票据连接 `/ws`，等待 `READY` 后发送 `JOIN` 并等待 `JOINED`。
5. 采用消息 UUID 关联发送与接收时间，记录 p50、p95、p99、失败率、连接总数、持续时间与重连次数。跨机器计时需要考虑时钟同步，或在同一测试进程记录往返。
6. 同时采集应用 CPU/内存、PostgreSQL 连接/锁/慢查询、Redis 指标；逐步增加并发，避免直接把未评估负载施加到生产服务。

## 数据库对照实验

至少准备 50,000 条消息，保留数据分布和房间消息量说明。在同一个只读测试数据库上，对比明确基线与游标查询的 `EXPLAIN (ANALYZE, BUFFERS)`，分别记录冷/热缓存条件和深页查询。不要在生产数据库中移除索引；基线实验应使用隔离数据库副本。

建议将真实报告保存到 `docs/benchmarks/`，包含提交 SHA、日期、硬件、实例数、配置、数据规模、测试命令和原始结果，再决定是否可以在项目介绍中引用性能数字。
